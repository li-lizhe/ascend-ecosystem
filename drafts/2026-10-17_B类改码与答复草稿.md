### B2. 四条答复草稿（英文原稿）

**给 finding 1（device probe）**

```
Verified — good catch, and I can reproduce it. With `check_available` left at its
default, `current_accelerator()` answers from the *compilation-time* accelerator,
so a build compiled with CUDA on a host with no visible CUDA device resolves to
`cuda:0` and the `is_available()` probes below never run.

Fixed in <sha>: the call is now `current_accelerator(check_available=True)`, with
a `TypeError` fallback for builds whose `current_accelerator()` takes no kwarg,
and the probe chain is kept for the `None` / raise paths.

Re-ran the resolution matrix with fake backends:
  compile-time CUDA, no visible device -> cpu   (was cuda:0)
  NPU present                          -> npu:0
  CUDA present                         -> cuda:0
  build without the kwarg              -> npu:0
```

**给 finding 4（torchaudio OSError）**

```
Agreed, and confirmed upstream: `torchaudio._extension._load_lib` documents that
when the library file is found but loading fails (a missing dynamic dependency,
i.e. the `ctype.DLL` `OSError`) it re-raises the exception as-is rather than
returning a bool. So `except ImportError` alone would miss exactly the case this
fallback exists for.

Fixed in <sha>: the import is now isolated in `_import_torchaudio_functional()`,
which catches `(ImportError, OSError)` and warns before returning `None`.
Verified by injecting an import that raises `OSError`: the fallback engages and
`linear_resample` still runs.
```

**给 finding 3（长度上界）**

```
Confirmed, and the amplification is larger than it looks: with the 8 MiB body
limit, `sample_rate=1` turns a ~1.49 M-sample request into a target length of
~2.39e10 samples — a ~89 GiB float32 allocation from one request.

Narrowing `sample_rate` to a plausible range (e.g. rejecting values above 384 kHz,
which is above any real audio rate and still far below the current ceiling) bounds
this without changing behaviour for real inputs, and `decode_request` is the
single place all three request paths go through. I'd rather do that than put an
arbitrary cap on the resampled length, since a legitimate 48 kHz -> 16 kHz
downsample is bounded by the body size already.

<要不要我按这个方向改？>
```

**给 finding 2（抗混叠滤波）**

```
This one is real but I don't think the fallback should try to be a band-limited
resampler: a correct implementation needs a windowed-sinc kernel (i.e. re-deriving
torchaudio's resampler), and the fallback only exists so the scorer degrades
instead of failing to import on hosts with no torchaudio wheel. Today it is
strictly better than the alternative (`ModuleNotFoundError` before this PR).

Two options, your call:
(a) keep the linear fallback and document the limitation (alias-free only for
    upsampling / equal rates) — I'd add that note next to `linear_resample`;
(b) drop the fallback entirely and let `transcribe()` fail with a clear message
    when a sample rate conversion is needed and torchaudio is missing.

I lean (a): on Ascend the resampler is only reached when the input is not 16 kHz,
and a hard failure there would make the whole scorer unusable on those hosts again.
```

## C. FunASR follow-up issue 草稿（英文，新建 issue；先建 issue 还是先回评论由你定）

**标题**：`[dist] XPU distributed backend selection (XCCL / oneCCL) is unverified — needs XPU hardware`

```
## Context

PR #3771 binds distributed training to the active accelerator instead of
assuming CUDA. Writing that change surfaced a second, independent defect on XPU:

`get_default_dist_backend()` returned `"nccl"` for every non-NPU device. Since
`get_accelerator_device_type()` does select XPU, an XPU run reached
`init_process_group(backend="nccl")` and could not start at all on a build
without NCCL — the same class of failure the PR fixes for Ascend NPU.

## Why this is not in #3771

The correct backend for XPU is XCCL (oneCCL; the legacy name on older builds is
`"ccl"`), so the fix is small:

    _ACCELERATOR_DIST_BACKENDS = {"npu": ("hccl",), "xpu": ("xccl", "ccl")}

but it advertises a runtime path that nobody here can exercise. We have no Intel
XPU hardware in our environment, so under the repository's hardware-validation
requirement the XPU arm was the only path #3771 changed without real-device
evidence. #3771 therefore keeps the historical `"nccl"` value for XPU — i.e.
exactly the pre-PR behaviour, unchanged — and the selection is tracked here for
whoever has the hardware.

## What a fix needs

1. Add the XPU entry above (keep `"ccl"` only for builds that positively confirm
   it through `torch.distributed.is_ccl_available()`).
2. Run an exact-head 2-rank `torchrun` on Intel XPU with XCCL, showing per-rank
   `xpu:0` / `xpu:1` binding, an `all_reduce`, DDP forward/backward, the
   end-of-epoch cache release, plus the exact PyTorch / oneAPI / device versions.
3. Extend `tests/test_distributed_device_setup.py` accordingly (the current test
   pins the narrowed behaviour: XPU stays `"nccl"` even when a build reports
   `is_xccl_available()`, so it will need to be flipped).

## Related

* #3771 — the Ascend NPU path, verified end to end on 910B2 hardware.
* Failure mode this is a follow-up to: `init_process_group(backend="nccl")` ->
  `RuntimeError: Distributed package doesn't have NCCL built in`.
```

### 中文要点

XPU 上 `get_default_dist_backend()` 对非 NPU 一律返回 `"nccl"`，而
`get_accelerator_device_type()` 会选到 XPU ⇒ XPU 上走 `init_process_group(backend="nccl")`，
在无 NCCL 的 build 上**根本起不来**。正确后端是 XCCL（老 build 叫 `"ccl"`），修法很小，
但它**广告了一条我们没人能跑的运行路径**；按仓库的硬件验证要求，#3771 里 XPU 臂是唯一没有真机证据的
路径，故 #3771 保持 XPU 为 PR 前的原值 `"nccl"`（行为零变化），选择逻辑另开本 issue。
issue 里写明了「修法 + 需要什么样的 XPU 证据 + 现有测试要翻转」，便于有硬件的人接手。

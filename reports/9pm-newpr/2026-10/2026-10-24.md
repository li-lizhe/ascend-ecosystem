## 四、缺陷与修法（一句话）

`EoraProcessor.process()` 每个模块结尾生成 `PROCESS_USED_MEMORY` 日志列时，直接调
`torch.cuda.memory_stats(DEVICE_0)`，且第二台设备只在 `torch.cuda.device_count() > 1` 时才统计；
而 `DEVICE_0`/`DEVICE_1` 来自 `auto_select_torch_device()`，在昇腾主机上它们是 `npu:0`/`npu:1`、
`torch.cuda.device_count()` 恒为 0 ⇒ **该列在 NPU 上恒为 `0.00MB`，且 4 卡机器也只报一台设备**。
`gptqmodel/looper/loop_processor.py` 的 `get_max_memory()` 是同一处 `torch.cuda` 写法。

修法（新增 1 个 callable 解析器 + 1 个取值函数，2 处调用点，CUDA 行为不变）：
在 `gptqmodel/utils/torch.py` 紧挨已有的 `resolve_empty_cache_callable()` / `empty_cache_for_device()`
新增 `resolve_memory_stats_callable(device_type)` / `memory_stats_for_device(device)`
（cuda/xpu/npu 各自解析，解析不到或取值失败一律返回 `{}`，保持「尽力而为」语义）；
EoRA 与 `get_max_memory()` 改用它，第二台设备的判据由「cuda 卡数 > 1」改为
「`DEVICE_1 != DEVICE_0` 且该设备能给出统计」。

## 六、对外正文（留痕：发出前先写在此，实际发出的即下方全文）

### 6.1 自建 issue 正文（English）

```markdown
### What happens

`EoraProcessor.process()` builds the per-module `PROCESS_USED_MEMORY` value from
`torch.cuda.memory_stats(DEVICE_0)` (and `DEVICE_1` only when `torch.cuda.device_count() > 1`).
`DEVICE_0` / `DEVICE_1` come from `auto_select_torch_device()`, so on a host whose accelerator is an
Ascend NPU they are `npu:0` / `npu:1` while `torch.cuda.device_count()` is 0.

The CUDA allocator reports nothing for a non-CUDA device, so on such a host that log row always reads
`0.00MB`, and the second-device branch is never taken even with several visible NPUs. `get_max_memory()`
in `gptqmodel/looper/loop_processor.py` uses the same `torch.cuda` query.

### Evidence on real hardware

Ascend 910B host (aarch64, 4 NPUs, `torch 2.15.0.dev` + `torch_npu`,
`torch.cuda.is_available() == False`, `torch.cuda.device_count() == 0`,
`DEVICE_0 / DEVICE_1 = npu:0 / npu:1`):

    torch.cuda.memory_stats(torch.device('npu:0')) -> 0 keys
    torch.npu.memory_stats(torch.device('npu:0'))  -> 123 keys

    # with 64MB held on npu:0 and 128MB held on npu:1
    current code                       -> 0.00MB
    accelerator-native allocator query -> 64.00MB, 128.00MB

### Expected behaviour

Allocator telemetry should ask the active accelerator, the way `resolve_empty_cache_callable()` /
`empty_cache_for_device()` already do for cache flushing, so NPU (and XPU) runs report real device
memory and the second-device branch is reachable whenever a second accelerator device exists.

I have a patch for this — a small helper in `gptqmodel/utils/torch.py`, the two call sites, and unit
tests — and will send a PR.
```

### 6.2 PR 正文（English；`Fixes #N`）

```markdown
## What

`EoraProcessor.process()` computed its per-module `PROCESS_USED_MEMORY` value with
`torch.cuda.memory_stats(DEVICE_0)` and only looked at the second device when
`torch.cuda.device_count() > 1`. `DEVICE_0` / `DEVICE_1` come from `auto_select_torch_device()`, so on a
host whose active accelerator is an Ascend NPU they are `npu:0` / `npu:1` while `torch.cuda.device_count()`
is 0: the CUDA allocator reports no statistics for those devices, the log row silently read `0.00MB`, and
the second-device branch was unreachable. `get_max_memory()` in `gptqmodel/looper/loop_processor.py`
carried the same `torch.cuda` query.

`resolve_memory_stats_callable()` / `memory_stats_for_device()` are added next to the existing
`resolve_empty_cache_callable()` / `empty_cache_for_device()` pair, and both call sites now use them. The
second-device condition becomes "`DEVICE_1 != DEVICE_0` and that device reports statistics", and CPU
behaviour is unchanged (telemetry simply stays empty when no allocator applies). CUDA results are
unchanged.

Fixes #N

## Verification

Real hardware: Ascend 910B host (aarch64, 4 NPUs, `torch 2.15.0.dev` + `torch_npu`,
`torch.cuda.is_available() == False`). The real `gptqmodel/utils/torch.py` was loaded from `main` and from
this branch on that host, and the log row was computed both ways while allocations were actually held on
two NPUs:

    DEVICE_0 / DEVICE_1 : npu:0 / npu:1
    allocated           : 64MB on npu:0, 128MB on npu:1
    PROCESS_USED_MEMORY, main  -> 0.00MB
    PROCESS_USED_MEMORY, patch -> 64.00MB, 128.00MB

    torch.cuda.memory_stats(torch.device('npu:0')) -> 0 keys (also after the allocations)
    torch.npu.memory_stats(torch.device('npu:0'))  -> 123 keys (tracks the allocation)

The five new unit tests in `tests/test_accelerator_memory_stats.py` fail on `main`
(`AttributeError: ... has no attribute 'memory_stats_for_device'`) and pass with this change. They were run
on the same Ascend host with a stand-in for the `monkeypatch` fixture, and `python -m py_compile` plus
`ruff check` (ruff 0.16.8 with `format/ruff.toml`) report no new findings for the changed files.

## Not tested

* End-to-end `gptqmodel` quantization with an EoRA adapter on the NPU host: that machine has
  `torch` / `torch_npu` but not the rest of the gptqmodel dependency set, so only the changed module was
  exercised there.
* Real CUDA and XPU devices: those paths are not modified, but they were not run here either.

## AI assistance

This change was prepared with AI assistance. The contributor reviewed the diff and this description and
approved publishing it.
```

## 四、缺陷与修法

**缺陷**：`xinference/model/image/ocr/` 下 6 个 transformers OCR 模型里，4 个用共享解析器，2 个仍是 CUDA 专属三元式：

```python
# unlimited_ocr.py:152（上游）
device = self._device or ("cuda" if torch.cuda.is_available() else "cpu")
# paddleocr_vl.py:71-76（上游）——显式 device 只要不是 "cpu" 就被丢掉
if self._device == "cpu":
    device, dtype = "cpu", torch.float32
else:
    device = "cuda" if torch.cuda.is_available() else "cpu"
    dtype = torch.bfloat16
```

对照（**同目录、同职责、已用共享解析器**）：`jina_ocr.py:82`、`navidc_ocr.py:101`、`ovisocr2.py:116`、`xiaomi_ocr.py:89`
都用 `device = self._device or get_available_device()`，dtype 用 `torch.float32 if device == "cpu" else torch.bfloat16`。

后果两条：
1. **非 CUDA 加速器上静默退回 CPU**：昇腾上 `torch.cuda.is_available()` 为 False 而 `get_available_device()` 返回 `"npu"`，
   这两个模型会把权重加载到 CPU（且 dtype 处理不一致：一个 float32、一个 bfloat16），不报错、不提示。
2. **PaddleOCR-VL 吞掉显式设备**：`device="cuda:1"` / `"npu:0"` 被替换成 `"cuda"`/`"cpu"`，用户指定的卡被无声忽略。

**修法**（设备无关、无 `if npu:` 分支，向仓内既有写法对齐）：

```python
device = self._device or get_available_device()
dtype = torch.float32 if device == "cpu" else torch.bfloat16
```

`iris.py` / `confucius4_tts.py` 存在同一三元式，但它们的第三方后端里有 CUDA 专属代码
（`thirdparty/iris3b/nn/attention.py` 调 `torch.cuda.get_device_capability`），本轮**不并入**，已在 PR 里说明。

### 6.1 issue 正文（自建，English）

标题：`PaddleOCR-VL and Unlimited-OCR ignore the configured device (and run on CPU on non-CUDA accelerators)`

```markdown
### Summary

`PaddleOCRVLModel.load()` and `UnlimitedOCRModel.load()` pick their load device with a CUDA-only
fallback, while every other OCR model in the same directory resolves it through the shared helper:

    # xinference/model/image/ocr/unlimited_ocr.py (before)
    device = self._device or ("cuda" if torch.cuda.is_available() else "cpu")

    # xinference/model/image/ocr/paddleocr_vl.py (before)
    if self._device == "cpu":
        device, dtype = "cpu", torch.float32
    else:
        device = "cuda" if torch.cuda.is_available() else "cpu"
        dtype = torch.bfloat16

    # jina_ocr.py:82, navidc_ocr.py:101, ovisocr2.py:116, xiaomi_ocr.py:89 (shared helper)
    device = self._device or get_available_device()

Two consequences:

1. **Silent CPU fallback on non-CUDA accelerators.** On Ascend NPU / XPU / MLU / GCU / MUSA,
   `torch.cuda.is_available()` is `False` even though an accelerator is present and
   `xinference.device_utils.get_available_device()` reports `"npu"`. Both models then load the
   weights on CPU without any warning - and with inconsistent dtypes (Unlimited-OCR resolves to
   `float32`, PaddleOCR-VL to `bfloat16`) - so a GPU/NPU host quietly serves OCR from the CPU.
2. **PaddleOCR-VL drops an explicitly requested device.** Any value other than exactly `"cpu"`
   (`"cuda:1"`, `"npu:0"`, ...) is discarded and replaced with `"cuda"`/`"cpu"`, so a user who
   launches the model on a specific device is not told that the request was ignored.

### Evidence (Ascend 910B4, real hardware)

torch 2.15.0.dev20260917+cpu + torch_npu 2.15.0.dev20260917+gitec69335, 1 x Ascend910B4
(ASCEND_RT_VISIBLE_DEVICES=7), `load()` driven with a stubbed `transformers` (no weights downloaded):

    get_available_device() -> npu | torch.cuda.is_available() -> False

    upstream cb46ea0f                          patched
    paddleocr_vl  device=None   -> cpu         paddleocr_vl  device=None -> npu
    paddleocr_vl  device='cuda:1' -> cpu       paddleocr_vl  device='cuda:1' -> cuda:1
    unlimited_ocr device=None   -> cpu         unlimited_ocr device=None -> npu

### Proposed fix

    device = self._device or get_available_device()
    dtype = torch.float32 if device == "cpu" else torch.bfloat16

as the sibling OCR models already do. Tests for the fallback and for an explicit device are in
the PR that references this issue.
```
### 6.2 PR 正文（发出前留痕）

标题：`fix(ocr): resolve the load device through the accelerator registry`

```markdown
## What

`PaddleOCR-VL` and `Unlimited-OCR` are the only two OCR models in `xinference/model/image/ocr/`
that resolve their load device with a CUDA-only fallback:

    device = self._device or ("cuda" if torch.cuda.is_available() else "cpu")

Their four siblings in the same directory (`jina_ocr.py`, `navidc_ocr.py`, `ovisocr2.py`,
`xiaomi_ocr.py`) all use `device_utils.get_available_device()`. This PR makes the two models use
the same helper, and derives the dtype from the resolved device (`torch.float32` on CPU,
`torch.bfloat16` otherwise) exactly as `navidc_ocr.py`/`ovisocr2.py` do.

Two defects are fixed:

1. On accelerators that are not exposed through `torch.cuda` (Ascend NPU, XPU, MLU, GCU, MUSA),
   the old fallback silently loaded the weights on CPU even though `get_available_device()`
   reports the accelerator. The dtype was also inconsistent between the two models.
2. `PaddleOCR-VL` discarded an explicitly requested device unless it was exactly `"cpu"`:
   `device="cuda:1"` or `device="npu:0"` was replaced by `"cuda"`/`"cpu"` without any warning.

Fixes #5777

## Changes

- `xinference/model/image/ocr/paddleocr_vl.py` - honour `self._device`, resolve the fallback
  through `get_available_device()`, pick the dtype from the resolved device.
- `xinference/model/image/ocr/unlimited_ocr.py` - resolve the fallback through
  `get_available_device()`.
- `xinference/model/image/ocr/tests/test_ocr_device_resolution.py` - new tests: fallback goes to
  the accelerator registry, an explicit device is honoured, an explicit `cpu` keeps `float32`.
```

## 七、流程与踩坑（新经验，已可复用）

1. **`npu_channel.py --exec` 的落地机不同，语义也不同**：读源码才发现 —— 落在 **169 时命令直接跑在宿主机 shell**，
   落在 **177 时才包一层 `docker exec npu-lizhe`**。所以「169 上没有 /opt/miniconda」这类结论要看清 header 的 `[通道 ssh:...]` 再下。
2. **新建昇腾容器必须 `--privileged`**：只挂 `--device=/dev/davinci*` + manager/svm/hdc 时
   `torch.npu.is_available()` 恒 False（`Can't get ascend_hal device count` / `DrvMngGetConsoleLogLevel failed(ret=4)`）。
   对照他人容器 `npu-x00475211` 的 HostConfig 才发现 `Privileged=true`；加上后立即可用（`npu available True / device_count 1 / Ascend910B4`）。
3. **bind mount 的 inode 陷阱**：`rm -rf` 重建挂载源目录后，**运行中的容器仍看到旧（空）目录**，`docker restart` 后才生效。
   踩了一次「/workspace 里什么都没有」的假故障。
4. **镜像里没有 Pillow**：`import PIL.Image` 直接 ModuleNotFoundError ⇒ 用 stub `PIL` 包（被测代码只拿它做类型注解）跑 pytest。
5. **本仓未强制 `ruff format`**：`.pre-commit-config.yaml` 只挂 `ruff-check`/`black`/`isort`/`mypy`；
   `ruff check`（E/F/W 选择集含 F401、W291）在本轮改动上全绿。
6. **`gh_push_files.py` 要分支先存在**（它 PATCH ref），且 blob 用 `raw.decode("utf-8")` 直推 ⇒

### 对外正文留痕（提交前已落盘，发出后不改写）

标题：`fix: keep the caller's speed for short text outside streaming`
head：`li-lizhe:fix/nonstreaming-short-text-speed` → base：`main`

```markdown
`infer_batch_process` ignores the `speed` a caller passes whenever the generated text is shorter than 10 bytes. `_infer_basic` sets `local_speed = 0.3`, which inflates the target duration of the generated segment by `speed / 0.3` — so `F5TTS.infer(..., speed=0.85)` on a 9-byte phrase asks the model for ~2.8x longer audio than requested, and the result comes out stretched / stutter-repeated with no warning.

Fixes #1331.

## Where it comes from

The clamp belongs to the streaming helper. `4ceba6d` ("This patch is to solve a problem where streaming will handle all of the client input") added `infer_batch_process_stream` with `local_speed = 0.3` for short chunks, where a longer target duration is wanted. `c3d415e` ("merging into one infer_batch_process function") removed the batch implementation — which used the requested `speed` directly — and made the streaming helper the single implementation, so the clamp has been applying to every call path since.

## Change

Apply the short-text clamp only when `streaming=True`, which restores the non-streaming behaviour that existed before the two helpers were merged. The streaming path is untouched.

```diff
     def _infer_basic(gen_text, fix_dur):
         local_speed = speed
-        if len(gen_text.encode("utf-8")) < 10:
+        # Short chunks need a longer target duration when they are generated one
+        # at a time for the streaming server. This must not override the speed a
+        # caller asked for anywhere else: the clamp was written for the streaming
+        # helper and only applies to the batch path because the two helpers were
+        # merged into this one.
+        if streaming and len(gen_text.encode("utf-8")) < 10:
             local_speed = 0.3
```

If the clamp turns out to be unwanted in the streaming path as well, dropping it there too is a one-line follow-up — I kept that behaviour unchanged here because it is the path the clamp was written for.

## Verification

The unmodified file (upstream `2f86664`) and the patched file were loaded side by side into the same harness: the heavy imports of `utils_infer` are stubbed, and the model / vocoder are recording stubs, so the harness observes exactly the `duration` argument `infer_batch_process` passes to `model.sample`. Reference audio 1.0 s @ 24 kHz, `ref_text="Hello world"`, `speed=0.85`.

| `gen_text` | bytes | `streaming` | upstream `duration` | patched `duration` | requested speed honoured |
|---|---|---|---|---|---|
| `Halobaba.` | 9 | False | **325** | **175** | before: no (0.3) / after: yes |
| `Hellobaba.` | 10 | False | 184 | 184 | yes, unchanged |
| `Halobaba.` | 9 | True | 325 | 325 | clamped in both, unchanged |

The 325 vs 175 difference sits entirely in the generated part of the duration (`232` vs `82` frames), a factor of `0.85 / 0.3 = 2.83` — the arithmetic the issue reports. The 10-byte case and the streaming case are byte-identical before and after, so the change is limited to the non-streaming short-text path.

Environment: torch 2.15.0.dev20260917+cpu (CPU), inside a container on an Ascend 910B host. The fix is pure control flow and does not depend on the device.

What was **not** run: end-to-end synthesis with the real checkpoint and vocoder (no model weights were downloaded), so the audio-level claim in #1331 is taken from the issue rather than re-measured here; and no CUDA/NPU hardware was exercised.

Signed-off-by: li-lizhe <147392333@qq.com>

### 对外正文留痕（提交前已落盘，发出后不改写）

标题：`fix(vram): keep the trainable parameters of the wrapped module`
head：`li-lizhe:fix/share-trainable-params-in-cast-to` → base：`main`

```markdown
`AutoWrappedModule.cast_to` rebuilds the wrapped module on every forward whenever the storage dtype and the computation dtype differ, which is what `--fp8_models` training does (`offload` / `onload` / `preparing` in float8, `computation` in bfloat16):

```python
return copy.deepcopy(module).to(dtype=dtype, device=device)
```

A LoRA adapter injected inside `.module` is then a trainable parameter **of the copy**. The backward pass writes the gradients into the copy, the parameters of `.module` keep `grad is None`, the optimizer never touches them and the adapters in the checkpoints are the ones they started from. `--find_unused_parameters` hides it: the run finishes with a normal-looking loss.

`AutoWrappedNonRecurseModule.cast_to` builds its copy the same way, so whole-block wrappers (Wan main DiT blocks, Vace, S2V) are affected too.

Fixes #1780.

## Change

After the copy has been cast, point its trainable parameters back at the parameters of the wrapped module, so a training step reaches the same `Parameter` objects the optimizer holds. Frozen weights are untouched and keep using the converted copy, so the reason the copy exists (a computation-precision view of frozen storage) is unchanged.

The wrapped module's own parameter objects are used as they are — no extra cast is applied to them here. If you would rather have the adapter moved to the computation dtype/device as part of the copy swap, that is a one-line addition to `share_trainable_parameters`; I kept it as the issue describes.

## Verification

The same block measured twice, upstream and patched, in one harness: an `nn.Linear` (frozen, storage float16) with a small trainable adapter inside it, wrapped with `offload`/`onload`/`preparing` = float16 and `computation` = float32, `onload()` called first as `base_pipeline.py` does before a forward, then one forward, one squared-error backward and one SGD step. The `grad` shown is read from the adapter parameters of the block that was wrapped — the ones an optimizer would have been given:

| device | wrapper | upstream | patched |
|---|---|---|---|
| CPU | `AutoWrappedModule` | `grad_A=None`, `grad_B=None`, weights unchanged | `grad_A=0.0413`, `grad_B=0.0563`, weights move 0.0056 |
| CPU | `AutoWrappedNonRecurseModule` | `grad_A=None`, `grad_B=None`, weights unchanged | `grad_A=0.0569`, `grad_B=0.0452`, weights move 0.0057 |
| Ascend NPU | `AutoWrappedModule` | `grad_A=None`, `grad_B=None`, weights unchanged | `grad_A=0.0193`, `grad_B=0.0500`, weights move 0.0050 |
| Ascend NPU | `AutoWrappedNonRecurseModule` | `grad_A=None`, `grad_B=None`, weights unchanged | `grad_A=0.0324`, `grad_B=0.0369`, weights move 0.0037 |

The "weights move" column is the largest absolute change of the adapter parameters after an SGD step, so it also says the update lands on the parameters that would be saved.

In both variants the frozen weight of the module that actually runs the forward is still the converted copy (checked by identity against the wrapped module's own weight), so the cast is not undone.

Environment: `torch 2.15.0.dev20260917+cpu` / `torch_npu 2.15.0.dev20260917+gitec69335` on 4x Ascend 910B, plus the same code on CPU. The float16/float32 pair stands in for float8/bfloat16: it is the same `storage dtype != computation dtype` branch of `cast_to`.

What was **not** run: the full FP8 LoRA training of Fibo-2.0-dev / Wan that the issue reports, and no `peft` was involved (the adapter is a minimal trainable module). This measures the gradient path through `cast_to`.

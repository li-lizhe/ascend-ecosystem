### 2.1 issue 正文（发布前留痕，English）

```markdown
### What happens

`gpu_memory_mode="model_group_offload"` reaches
`safe_enable_group_offload(pipeline, onload_device=device, offload_device="cpu", offload_type="leaf_level", use_stream=True)`,
and the vendored group-offloading helper (`videox_fun/utils/group_offload.py`, derived from
`diffusers/hooks/group_offloading.py` v0.36.0) creates its data-transfer stream by probing CUDA and XPU only:

    if use_stream:
        if torch.cuda.is_available():
            stream = torch.cuda.Stream()
        elif hasattr(torch, "xpu") and torch.xpu.is_available():
            stream = torch.Stream()
        else:
            raise ValueError("Using streams for data transfer requires a CUDA device, or an Intel XPU device.")

On a host whose accelerator is neither (Ascend NPU here) `torch.cuda.is_available()` is False and there is no
XPU branch, so the mode fails before any hook is installed, even though the accelerator's backend does
implement streams.

### Evidence on real hardware

Ascend 910B host (aarch64, 4 NPUs, `torch 2.15.0.dev20260917+cpu`, `torch_npu 2.15.0.dev`,
`torch.cuda.is_available() == False`, `torch.npu.device_count() == 4`), with the file loaded unchanged from
`main` (leaf imports stubbed):

    apply_group_offloading(model, onload_device=torch.device("npu:0"), offload_device="cpu",
                           offload_type="leaf_level", use_stream=True)
      -> ValueError: Using streams for data transfer requires a CUDA device, or an Intel XPU device.

    torch.npu.Stream() -> <torch_npu.npu.Stream device=npu:0 npu_stream=0x...>

### Expected behaviour

The stream should be resolved from the onload device's own backend, so any accelerator whose backend
implements streams can use this mode, while devices that cannot stream are still rejected. That is what
upstream diffusers does in the function this file is derived from.

I have a small patch for this and will send a PR.
```

### 3.1 PR 正文（发布前留痕，English）

```markdown
## Problem

`ddp_init_group()` assumed the accelerator is CUDA:

* the rank -> device guard was sized with `torch.cuda.device_count()`, and
* the backend whitelist was nccl/gloo/mpi.

On a host whose accelerator is not CUDA (Ascend NPU through `torch_npu`, whose collective library is
`hccl`), `torch.cuda.device_count()` is 0, so every rank aborted with

    ValueError: Killing process
    Not enough GPUs available!

before `init_process_group` was ever reached — even with 4 NPUs visible — and `hccl` was rejected as a
backend that "doesn't exist" even though PyTorch reports it as available. This is the same device-agnostic
migration that `infer_device()` went through in #3080; the distributed launch path was left behind.

## What

* the device count for the guard, and the per-rank device binding, now come from
  `torch.accelerator` (`current_accelerator().type`, `device_count()`);
* the nccl/gloo/mpi checks stay as they are, and any other backend that
  `torch.distributed.is_backend_available()` reports as available is accepted (Accelerators other than
  CUDA ship their own collective library, e.g. `hccl` for Ascend NPU).

CUDA hosts keep the previous behaviour: backend `nccl` and `torch.cuda.set_device(device)`.

## Verification

Real hardware: Ascend 910B host (aarch64, 4 NPUs, `torch 2.15.0.dev`, `torch_npu 2.15.0.dev`,
`torch.accelerator.is_available() == True`, `current_accelerator() == npu`, `device_count() == 4`,
`torch.cuda.is_available() == False`). `speechbrain/utils/distributed.py` from `develop` and from this
branch was loaded by file path on that host, and `ddp_init_group({"distributed_backend": "hccl"})` was run
through `torchrun --nproc_per_node=2`:

    develop: [rank 0] FAILED ValueError: Killing process / Not enough GPUs available!
             [rank 1] FAILED ValueError: Killing process / Not enough GPUs available!
    branch : [rank 0] ddp_init_group OK | pg backend=hccl world_size=2
             [rank 1] ddp_init_group OK | pg backend=hccl world_size=2
             [rank 0] all_reduce sum=6.0 on npu:0   (two elements per rank, values rank+1)
             [rank 1] all_reduce sum=6.0 on npu:1

The repository's own test file was run on the same host against the real module (`pytest` 8.3.2, with the
package skeleton in place): `8 passed` with this change. With the `develop` module and the three new tests,
`2 failed, 1 passed` — the failure is the "Killing process" guard above.

## Not tested

* A real CUDA/nccl host — the code path is written as before (`torch.cuda.set_device`) but was not executed
  on a GPU machine.
* The `mpi` backend.
* End-to-end speechbrain recipe training: that host has torch/torch_npu but not speechbrain's runtime
  dependencies, so the real module and the repository's own tests were driven instead.
```

### 4.1 PR 正文（发布前留痕，English）

```markdown
## What

`get_autocast_dtype()` and `is_autocast_enabled()` in `timm/layers/fast_norm.py` fall back to the
device-specific autocast functions on torch builds without the device-generic API (torch <= 2.3):

    except (AttributeError, TypeError):
        # dispatch to older device specific fns, only covering cuda/cpu devices here
        if device == 'cpu':
            return torch.get_autocast_cpu_dtype()
        else:
            assert device == 'cuda'
            return torch.get_autocast_gpu_dtype()

For any other accelerator type the `assert` fires. Those accelerators publish the same information on their
own namespace -- `torch.npu.get_autocast_dtype()` / `torch.npu.is_autocast_enabled()` on Ascend NPU -- which
is what the device-generic API returns on a newer build. The fallback now asks the device's own namespace
first, and still ends at the cuda/cpu functions; `device='cuda'` and `device='cpu'` are unchanged.

This is reachable from `timm.layers.fast_*_norm` (used by `--fast-norm` runs, `set_fast_norm()`), where the
device string comes from `x.device.type`. On a newer torch the generic API answers and hides it; on the torch
versions paired with these accelerators (2.1-2.3) it raises.

## Verification

Ascend 910B host (aarch64, 4 NPUs, torch 2.15.0.dev, torch_npu 2.15.0.dev, `torch.cuda.is_available() == False`,
`torch.accelerator.current_accelerator() == npu`). `timm/layers/fast_norm.py` was loaded from `main` and from
this branch on that host, and the legacy path was exercised by emulating a torch build without the
device-generic API (attribute removed, zero-argument predicate restored -- the state of torch <= 2.3):

    main  : get_autocast_dtype('npu')  -> AssertionError
            is_autocast_enabled('npu') -> AssertionError
    branch: get_autocast_dtype('npu')  -> torch.float16
            is_autocast_enabled('npu') -> False

    cpu and cuda answers are identical before and after in both modes; with the real torch 2.15 all three
    device types answer identically before and after, since the generic API takes over.
    fast_group_norm on a real npu:0 tensor matches F.group_norm (max abs diff 0.0e+00).

The new test in `tests/test_layers.py` asserts the same behaviour without hardware.

## Not tested

* A torch 2.1-2.3 build on an NPU: that combination is what triggers the old `assert`, but only
  torch 2.15 + torch_npu was available here, so the legacy path was emulated rather than run on an old runtime.
* A CUDA host: the cuda/cpu branches are unchanged from the previous code but were not executed on a GPU.
```
